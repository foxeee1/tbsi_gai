# M1 MCCA Message Adapter Matched G0/G1 (2026-10-10)

## Question

Does adapting the already-computed template MHSA cross-modal messages improve short-proxy tracking over a matched M1 continuation, while preserving the original TBSI/search-fusion/CENTER path?

## Hypothesis and controlled change

G0 is M1 epoch-15 continuation for 3 epochs. G1 is identical except that the RGB-query/TIR-value and TIR-query/RGB-value messages at the three existing TBSI-E template MHSA locations pass through separate bottleneck adapters. Their final projections are zero-initialized, so G1 starts exactly at the G0 forward function. No new loss, no changed optimizer, and no replacement attention/fusion/head are included.

## Follow-up Audit and Attribution (2026-10-11)

The split audit confirms zero sequence overlap between the 176-sequence RPP train subset used for both continuations and the 60-sequence RPP test proxy. This protects sequence-level separation for the *continuation* comparison, but the 60-sequence proxy has already been inspected and must not be described as a fresh dev set.

Paired sequence bootstrap (50,000 replicates; seed `20261011`) gives 95% percentile intervals: AUC `[−0.162, 3.664]`, PR `[−0.443, 4.205]`, and NPR `[−0.169, 4.392]`; all include zero. The mean deltas remain positive, but sequence-level uncertainty is too wide to claim robust improvement. Full output: `output/experiments/M1_MCCA_G0_G1_20261010/bootstrap_and_isolation.json`.

The G0/G1 configs differ only in `MCCA_MODE` (`off` versus `bidirectional`); shared hashes confirm the exact same epoch-15 parent, train176 list and manifest, test60 list and manifest, seed 42, 3 epochs/252 optimizer steps, batch/accumulation, FP32, worker count, optimizer/schedule, and evaluator command family. The standard trainer seeds sampling and augmentation from seed 42 in both arms. The continuation comparison is therefore matched at the registered contract, with unavoidable stochastic training trajectory differences from the extra parameters.

For direction attribution, two default-off-per-direction config gates were added. In an eval-mode operator check using the trained G1 adapter tensors, explicit-both was bitwise identical to the default-both path; disabling either single direction changed output (max absolute differences `0.0305` and `0.0268` on a fixed synthetic input). The gates leave all parameters present for checkpoint loading and skip only the selected adapter's forward computation. This verifies intervention semantics, not tracking utility.

A 96-sequence outcome-blind train-side cohort was fixed before this follow-up (sequence-list SHA256 `b27b6a0426cc8e5c05a4cfe1ddf86b392768fe5c7b386f72c74622b03e5bbf3b`). It is disjoint from both the continuation train176 and test60 lists. It is a holdout from this 3-epoch continuation, not an unseen split relative to the pretrained M1 parent. The first attempt to evaluate it failed before any frame because the test-split dataset loader pointed at `testingset`; the failure is preserved in `m1_mcca_fresh96_loader_preflight_failure_20261011.md`. A dedicated `trainingset` loader was added, and the versioned `_V2` serial run completed all four arms on the same 96 sequences.

Because runs were not alternated/repeated and this order is confounded with runtime conditions, these numbers do not establish stable adapter overhead; the recommended repeated alternating timing test remains undone. Do not infer that one direction is faster from these single-pass numbers.

Final decision: the initial test60 result remains a positive but heterogeneous screening signal; it did not replicate on the disjoint-from-continuation fresh96 cohort. Neither direction-only intervention beat G0, and no direction is promoted. Keep MCCA as an unconfirmed research candidate only; do not start full training/test or tune on either observed cohort. ## Preflight incident

The first full G0 model-construction check stopped before training because YAML parsed unquoted `MCCA_MODE: off` as boolean `false`; the explicit feature-mode validator correctly rejected it. No optimizer step, checkpoint, or GPU training process was started. The value is now quoted as `'off'`, and the corrected configuration is revalidated before launch. The initial implementation snapshot remains preserved as `source_snapshot.tar.gz`; the corrected run snapshot is `source_snapshot_v2.tar.gz`.

The first launcher attempt exited at the protected M1 config hash guard because its expected SHA256 literal omitted the final `e`; the protected file itself matched its registered hash. The launcher constant is corrected. No training, tracking, or checkpoint output was produced by that invocation.
